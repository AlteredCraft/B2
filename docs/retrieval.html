Inside b2 search & b2 similar

The two retrieval flows, stage by stage, each stage anchored to the function that implements it. Both adapters — the CLI and the desktop app — call the same Vault façade reads, so the rows a surface shows are computed once, identically. The code is ground truth; this page is a projection of it. New to the ideas? Start with the plain-language concepts explainer.

1Two questions, two postures

Search and similarity read the same index and end in opposite disclosure rules — deliberately, because they answer different kinds of question.

Flow ② — search

"What in my vault matches this query?" has an honest zero, so a served result is a claim of evidence: a query the vault holds no lexical or semantic evidence for answers "no matches" and serves none of its nearest guesses (invariants D2, ADR-0015).

Flow ③ — similar

"What belongs next to this note that I haven't linked?" is relative — everything in a vault is somewhat related to everything — so the ranked list is always served and no anchor-local statistic gates it (invariants D1, ADR-0014). You are the judge.

A near-neighbour of both that is neither: graph_filtered_search (search.rs) is the vector⨝graph scoped-traversal primitive — "nearest chunks whose note is within k typed hops of an anchor" (near ∩ connected). Discovery is its complement (near ∖ connected). And vector_only_search is the eval harness's ablation instrument, never an adapter surface.

2Flow ② — search, from query to served rows

crates/b2-core/src/search.rs · vault.rs — entry: Vault::search_evidence (the CLI's cmd_search adds --exclude via search_evidence_excluding; the desktop's `search` command is the same read)

Hybrid retrieval: BM25 over chunks_fts ⊕ brute-force vector KNN over embeddings, fused by Reciprocal Rank Fusion, resolved from chunks up to notes, and served with the evidence verdict that lets a surface say "no matches" honestly.

keyword (BM25) semantic (vector) the evidence reading fail fast
  • Width is a quality knob, not plumbing. The façade asks retrieval for a hit pool over its limit, and each signal widens that again (pool_size = 5×, min 30) before RRF fuses. The note view keeps 3× (dedup collapses chunks onto notes); the passage view (search_chunks — chat's retrieve step) keeps only limit + 2, torn-read headroom, because RRF over a wider candidate set returns different answers, not more of them — width moves only on measured relevance (GH #141/#142).
  • BM25-only is a smaller projection, never an error. On a projected-but-unembedded vault the vector half is absent; the same fusion runs over the single BM25 list, so scores stay on one scale — and best_cos is honestly None.
  • --exclude subtracts rows, never evidence. The follow-up-search flag for agent loops removes caller-named paths from the served rows; the verdict and its signals still read the whole vault, and a heavily-excluded query may honestly under-fill.

Three verdict states, three behaviours

The verdict is lexical OR semantic — two independent signals, because one test cannot tell nothing here matches from everything here matches. The lexical anchor is IDF-weighted term coverage (a stopword is a measurement, never a shipped word-list); the semantic backstop is the best cosine. The bar is calibrated per embedding model in the eval harness; its values live in search::BGE_BASE_EVIDENCE_BAR and are re-justified on every make eval run — deliberately never quoted in prose.

3Flow ③ — similar, the two-stage discovery scan

crates/b2-core/src/discover.rs — candidates · vault.rs — Vault::similar · CLI cmd_similar · desktop Similar pane
Free & local
b2 similar makes zero model calls and touches no network.

Discovery is a pure read over stored vectors: the anchor is represented by the chunk vectors a prior reindex wrote — never an embed_query of its text (bge's asymmetric query prefix is the wrong side of the space) — which is why the CLI opens the vault with the fake embedder and still serves real-model rankings. Running it a hundred times costs what running it zero times does. You are the precision gate: there is no suggestion queue and nothing "inert until accepted" — a connection exists only once you write it.

vectors — KNN & max-sim (no model) graph — the ∖ already-linked exclusion the ranked list you read
  • The shortlist is a recall device, never a quality gate. Stage 1 exists only to avoid scoring the whole vault; on any vault at or below 200 candidate notes the two-stage result is exactly the whole-space scan's, which is what keeps the shape a pure performance device (GH #38, #192).
  • The 1-hop exclusion is the graph's only role. The anchor and its direct neighbours are skipped up front, so they never occupy a shortlist slot. A 2-hop note — the triadic-closure candidate, "you linked A–B and B–E but never A–E" — survives, ranked purely by semantic score.
  • Max-sim, not centroids, decides the score. A note's centroid shortlists it; its single best chunk-pair ranks it, and that chunk rides along as the evidence passage the surface shows — so one strong section inside a messy note still counts (the buried gem).
  • The list is served whole, graded where a statistic exists. The ranked list is always served — limit is a cap that under-fills only for want of scorable notes, and no anchor-local statistic ever empties the pane: such a test cannot distinguish nothing is related from everything is related (invariants D1; the measurements are ADR-0014's record). The per-candidate z is computed against the anchor's own candidate population and gates nothing: it paints the desktop's strength band. Under 12 candidates, in a space with no spread, or on a fake-embedded space, no z exists — the list is served ungraded, and the surface says so.
  • Empty means "nothing to compare", never "nothing relates". At a nonzero ask, an empty list means no unlinked note has stored vectors yet (or the space isn't semantic) — the CLI's two empty states say exactly that.

4From the list to a link — b2 link

design/data-model.md §4 · crates/b2-core/src/note.rs — add_relation

The list is candidates, not connections. You commit the ones worth keeping — two ways, both authored in Markdown, and only one can carry a stance.

# 1 — surface the nearest not-yet-linked notes (free, local, instant)
b2 similar espresso-extraction.md
  0.8143  dialing-in-grind (notes/dialing-in-grind.md)
      Finer grinds raise extraction pressure; past a point the shot chokes and turns bitter…
  0.7920  brew-temp (notes/brew-temp.md)
      Temperature stability matters as much as the target — a swing mid-shot muddies the cup…
# stderr: Commit one with:  b2 link espresso-extraction.md <note> --type <verb>

# 2 — commit the one worth keeping; you pick the type (defaults to `references`)
b2 link espresso-extraction.md notes/dialing-in-grind.md --type supports \
        --explanation "grind size sets the extraction pressure"

What changed on disk is one line, in the source note's frontmatter — the body is untouched:

 b2_relations:
+  - "supports [[notes/dialing-in-grind.md]] — grind size sets the extraction pressure"
An edge exists iff it's in the Markdown. b2 link appends one typed-link line and re-projects the note, so the edge materializes as origin=frontmatter from the line just written — a projection of an authored line, never an index mutation. A body [[link]] you write yourself is the other way, always untyped references. To undo either, delete the line; it's gone on the next reindex. Re-run b2 similar afterward and the linked note drops off the list — it's connected now, so the exclusion filters it. The verb palette is the closed stance core — references · supports · contradicts — and a hand-written tail verb is kept verbatim (ADR-0010).
