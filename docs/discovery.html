Deep dive · the discovery run

Inside b2 similar

Exactly what happens when you run b2 similar: a pure, local vector KNN over the embeddings your index already holds, surfacing the notes most similar in meaning to one you name — minus the ones you've already linked — each with the passage that made it similar. No model call, no network, no cost. You read the list; b2 link commits the ones worth keeping. A companion to the architecture's candidate engine.

⚡Free & local
b2 similar makes zero API calls and touches no network.

Discovery is a vector KNN over your already-stored embeddings — it reads vectors straight back and re-embeds nothing, so a run is instant and costs nothing per note, per pair, or per token. The only embedding work is the one-time b2 reindex that built those vectors in the first place. You are the precision gate — you decide which surfaced notes deserve a real connection and author it. There is no suggestion queue, nothing "inert until accepted": a connection exists only once you write it.

Prerequisite — a real-model index. similar reads the vectors + typed graph a prior b2 reindex wrote — it reads stored vectors straight back and never re-embeds, so it needs no model and no API key of its own (it calls nothing). But if that index was built under B2_EMBEDDER=fake, the vectors are blake3 hashes, not semantics, and the neighbours it surfaces are meaningless. For real discovery the order is b2 init → b2 reindex (real model) → b2 similar.

1The pipeline, per anchor

crates/b2-core/src/discover.rs — the candidates fn · crates/b2-cli/src/main.rs

You name one note — the anchor. B2 reads its stored chunk vectors, subtracts the already-linked set up front (the anchor plus its 1-hop graph neighbours — the ones you've linked), shortlists what's left by per-note centroids (one cheap O(notes) scan), judges the quality floor against that full centroid field, scores each surviving shortlisted note by its best exact chunk-pair match, ranks, and lists up to N. Every step is vector math and a graph read — no model, no network.

vectors — KNN & max-sim (no model) graph — the ∖ already-linked exclusion the ranked list you read

A candidate is a note near the anchor in embedding space but not already connected — the complement of the graph, not the intersection. Generation is deliberately permissive: it over-produces and leaves the judgment to you. Two honesty notes baked into the code: it is passage↔passage — the anchor is represented by the vectors already in embeddings, never by an embed_query of its text (bge's asymmetric query prefix is the wrong side); and the 1-hop exclusion is the graph's only role — graph-distant "bridge" notes ride along unboosted, so a transitively-related note two hops away still surfaces.

Ground truth: discover::candidates(conn, anchor, limit, floor) (crates/b2-core/src/discover.rs) — stage 1: one db::for_each_note_centroid scan ranks every note by centroid distance to the anchor's centroid (computed in-process from its chunk vectors), with graph::reachable_within(anchor, 1) excluded up front and a shortlist many times limit kept; stage 2: exact max-sim over only the shortlist's chunk vectors, keeping each note's best pair and its evidence chunk. The quality floor (below) is judged on the full stage-1 population before any truncation; the result sorts by score with a path tie-break and truncates to limit. Returns empty when there's no embedding space, the anchor has no chunks, limit == 0 — or when the floor says nothing genuinely relates. Vector-only; re-embeds nothing.

2The quality floor — zero is an honest answer

crates/b2-core/src/discover.rs — DiscoveryFloor · docs/design/index-engine.md §3 · GH #150

limit is a cap, not a promise. On any real vault, ten notes are always nearest — even when nearest means nearest-of-nothing. So surfacing is quality-gated: when nothing in the vault genuinely relates to the anchor, b2 similar says so with an empty list instead of serving ten weak cards.

The rule is a per-anchor z-score, judged against the anchor's own stage-1 centroid-distance population (which every call already computes, so it costs nothing): a leader gate suppresses the whole list when even the best candidate stands too little above that field — one diffuse cloud has no signal — and a member bar ends the list where candidates rejoin it. Because a z-score is relative to the anchor's own distribution, the floor is model-relative by construction: no recorded cosine constant, nothing to recalibrate on a model or device swap. It stays inert on tiny vaults (fewer than a dozen candidates — you can see everything anyway) and never applies to a fake-embedded space. Calibrated on the eval's hand-labelled anchors and transfer-checked at the opposite density extreme (GH #150, 2026-08-11).

Escape hatch: b2 similar --no-floor (the desktop pane's Show nearest anyway) shows the raw nearest, however weak — Vault::similar_raw, one call, no configuration. Each surfaced candidate also carries its z, which is what the desktop's strength band is derived from — never the raw score.

3What a run costs

The short version: nothing, and it's instant. b2 similar is a local KNN over vectors already on disk — it makes no network request, loads no model, and spends no tokens. There is no per-note, per-pair, or per-token bill because there is no model in the loop at all.

The only cost is the index

Embedding happens once, in b2 reindex, when your vectors are written. similar reads those vectors straight back; running it a hundred times costs exactly what running it zero times does. Re-embedding only happens when a note changes and you reindex again.

Scale & the tuning lever

Cost scales with note count (the stage-1 centroid scan) plus the shortlist's chunks — CPU-bound vector math, milliseconds on a personal vault. Two knobs: --limit caps the list, and --no-floor shows the raw nearest the quality floor would hold back. Both change what you read, never what you pay. No API key, no config table, no rate limit.

# the real path — build the index once, then discover for free, forever
b2 init                       # provision the real embedder (one time)
b2 reindex                    # embed the vault — the only embedding cost
b2 similar espresso-extraction.md    # instant local KNN — no model, no network, no tokens
Deterministic and re-runnable. Candidate generation is pure vector math over stored data — same index, same anchor, same ranked list every time (ties broken by path). Run it as often as you like; it writes nothing and changes nothing.

4From the list to a link — b2 link

docs/design/invariants.md · docs/design/data-model.md §4

The list is candidates, not connections. You pick the ones worth keeping and commit them. Two ways, both authored in Markdown — B2 supplies the mechanics, you supply the judgment and the type. They are not interchangeable: only one of them can carry a stance.

write a body link yourself

Type a [[path]] (or [[path|title]]) anywhere in your note's body. That edge is always untyped — a plain references, no verb, no "why": the body has no B2 syntax to express one, by design, so your prose stays prose. B2 reads it on the next reindex; it never writes your body.

or run b2 link

b2 link <src> <dst> [--type <verb>] [--explanation …] appends one typed-link string to the source note's frontmatter b2_relations: — Markdown-first, never the body — then re-projects that note so the edge materializes as origin=frontmatter, active.

A worked example

b2 similar espresso-extraction.md surfaced dialing-in-grind as its nearest unlinked note. You agree it's load-bearing — the shot depends on the grind — so you commit it with the verb you choose from the core vocabulary:

# 1 — surface the nearest not-yet-linked notes (free, local, instant)
b2 similar espresso-extraction.md
  0.8143  dialing-in-grind (notes/dialing-in-grind.md)
      Finer grinds raise extraction pressure; past a point the shot chokes and turns bitter…
  0.7920  brew-temp (notes/brew-temp.md)
      Temperature stability matters as much as the target — a swing mid-shot muddies the cup…
  0.7614  tamping (notes/tamping.md)
      An even tamp keeps the puck flat so water can't channel down one side…
# stderr: Commit one with:  b2 link espresso-extraction.md <note> --type <verb>

# 2 — commit the one worth keeping; you pick the type (defaults to `references`)
b2 link espresso-extraction.md notes/dialing-in-grind.md --type supports \
        --explanation "grind size sets the extraction pressure"
Linked espresso-extraction.md —supports→ notes/dialing-in-grind.md. Wrote the relation into the source note's frontmatter.

What changed on disk is one line, in the source note's frontmatter — the body is untouched:

 b2_relations:
+  - "supports [[notes/dialing-in-grind.md]] — grind size sets the extraction pressure"
An edge exists iff it's in the Markdown. There is no suggested or rejected status and no review queue to survive a rebuild — drop the index, reindex, and the edge comes back because it's in your note. A committed edge is pristine: just the <verb> [[path]] line, no by, confidence, or provenance stapled on. To undo one, delete its b2_relations: entry; it's gone on the next reindex.
Ground truth: the core vocabulary is the closed three-verb stance set in relation::CORE — references (neutral) · supports (for) · contradicts (against) — which is your typing palette on b2 link --type, and the only thing it accepts. Three, because stance is precisely what the vectors can't tell you: they already found that these two notes are about the same thing. A verb outside the core, written by hand into b2_relations:, is kept verbatim and treated as opaque. Mirrored across data-model.md §4, index-engine.md §3, and invariants.md.
