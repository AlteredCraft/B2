B2 — how the system is built

B2 is a local-first Markdown vault with an AI layer that surfaces semantically similar, not-yet-linked notes for you to connect. This repo is the index engine + its two adapters (the b2 CLI and a Tauri desktop app): a SQLite store treated as a disposable projection of your Markdown — nothing durable outside your notes — a real local embedder behind the embedder seam, and the typed Vault API both adapters drive. This page traces the whole architecture through one real vault — the two-note fixture the test suite runs on — so every claim is concrete and checkable.

model-free · deterministic suite 4 crates: b2-core · b2-embed · b2-cli · b2-desktop Rust 1.96 · edition 2021 v1 kernel: init · reindex · status · search · similar · link · neighbors · explain · add · write · mv · rm

The suite is integration-first: most tests open a real SQLite database, ingest a real vault on disk, and assert on the resulting projection — so it describes the built system, not mocks of it. Nothing is #[ignore]d; the checks that need the real embedder live in the out-of-CI eval harness, which runs on demand and therefore actually runs. The LLM relator was cut 2026-07-04 (per-pair cost didn't scale) — its crate, seam, and suggestion queue are gone; connection discovery is now local, free, and instant.

The governing equation

One equation shapes every decision. Keep only this:

index = projection of ( Markdown )
Markdown vault → ingest → b2.sqlite (disposable) → search · neighbors · explain · similar

Delete b2.sqlite, rebuild it from the Markdown — it must come back identical. Exactly one thing is durable and un-derivable: your Markdown (the source of truth for both knowledge and every committed connection). There is no state anywhere outside your notes. Everything downstream is this equation defended. (Through 2026-06-30 a third tier — a durable .b2/log/ event log holding the suggestion queue + rejection memory — closed an ∪ log term; the 2026-07-04 relator cut removed the only thing it was for, so the log tier is gone and the equation simplified.)

Tier 1 · Markdown — source of truth

Notes + every committed edge, plain .md, fully usable in Obsidian with no B2. Stays pristine — B2's only writes are surgical and in frontmatter; the body is 100% the human's.

Tier 2 · b2.sqlite — disposable cache

FTS5 + plain vector tables scored in-process + the typed graph. Disposable: holds nothing that can't be reconstructed from the Markdown. Drop it, reindex, get an identical index.

A whole vault is one portable folder: the index lives under <root>/.b2/, a dotfolder Obsidian and the vault scanner both ignore. Point B2 at a folder of Markdown — that is the entire setup.

Four crates, cleanly layered

The engine owes nothing to the two adapters above it or the one model beside it. The AI-heavy crate sits behind the Embedder trait defined in b2-core, so the engine and its whole fast suite never import a tensor — and adding the desktop UI added one adapter, not new architecture.

b2-core · the engine

Turns a folder of Markdown into a queryable index and keeps it a pure function of disk. Model-free (no candle, no network) so its suite is fast and deterministic. rusqlite (bundled SQLite + FTS5), blake3, yaml — no vector extension: vectors are plain tables scored in-process (#38).

  • note · ingest · chunk · link · relation
  • db · graph · search · discover
  • embed · llm — the two seams + their fakes
  • add · mv · vault (the façade)
b2-cli · the adapter

The b2 binary. Holds no engine logic: parse args, pick + inject the embedder, call the Vault façade, print (human, or --json for agents). Funnels every error through user_message so nothing internal leaks.

b2-desktop · the GUI adapter

The Tauri host — the GUI sibling of b2-cli, equally logic-free: each #[tauri::command] is deserialize → one Vault call → serialize, reusing the CLI's --json view types as the IPC contract. The ui/ frontend (Vite + vanilla TS) renders the read → discover → link loop; two adapters over one façade can't drift.

b2-embed · the real embedder

LocalEmbedder: candle-backed BERT, BAAI/bge-base-en-v1.5 (768-dim, ungated), pure-Rust inference. b2 init downloads + verifies it into a shared XDG cache. Implements embed::Embedder — the one seam with a real implementation shipped today.

Ground truth: the layering is enforced by where deps live. b2-core's Cargo.toml has no candle and no HTTP client; the whole engine suite runs on the deterministic fake embedder. The real model is reached only by b2 init + the out-of-CI retrieval eval. Cut 2026-07-04: a former crate, b2-relate (the Claude-backed relator), was removed with the LLM discovery pipeline — see Flow ③.

FLOW ①  Ingest — vault becomes index

crates/b2-core/src/ingest.rs

b2 reindex is the write path that realizes the governing equation. Since 2026-07-07 it composes two separately-invokable passes: model-free project_vault (notes, chunks, FTS, edges) and embed_vault (fill the DB-derived set of chunks still missing a vector). Projection's one subtlety: a note can link to one the walker hasn't reached yet, so link resolution must not depend on file order — it runs in two phases.

walk *.md (dotfolders skipped, sorted) → Phase 1 · notes + chunks (+FTS) → fills the path set → Phase 2 · edges → embed pass · fill missing vectors
  • Phase 1 projects each note's frontmatter and chunks its body (the structure-aware qmd chunker: ~450-token target, overlapping, cut at Markdown breaks, each chunk stamped with its heading_path breadcrumb); chunk text lands in chunks_fts immediately, so keyword search works before anything is embedded. This fills notes(path) — the set of paths a link may resolve to — for the whole vault.
  • Phase 2 derives edges by parsing each body's links + frontmatter b2_relations: and resolving every [[path]] against the now-complete resolver. From spaced-repetition.md that's two directed edges to memory.md: a bare body references and a typed frontmatter supports. Body links are always untyped — the verb and explanation come only from b2_relations:.
  • Ingest writes nothing. A note's identity is its vault-relative path, so there is no id to mint and no line to add — the file B2 read is the file B2 leaves (GH #170). Before that, phase 1 stamped a missing b2id: into the frontmatter; a stamp is not durable state the index needs, and the path already names the note uniquely, so the write went away with it.
  • The embed pass then batches every chunk still missing a vector through the seam into embeddings — metered (per-batch progress) and cooperatively cancellable, which is what lets the desktop run it in the background. Our two notes yield one chunk each; memory.md's chunk lands in embeddings ready to be found. A projected-but-unembedded vault is already browsable: keyword search works, and search degrades to BM25-only rather than failing.

Incremental by default, ≡ a full rebuild. A note whose body_hash is unchanged and whose chunks all still have vectors reuses them verbatim — only edited notes re-embed, and since vectors are addressed by the hash of the text that produced them, only genuinely new text costs a model call. Both paths replace rather than accumulate: re-projecting a note deletes its old chunks (FTS triggers fire) and all its edges, then re-derives every edge from the current Markdown (body inline ∪ frontmatter). Because every edge is Markdown-derived, a one-note re-parse is exactly a one-note slice of a full rebuild — there is no log term to reconcile. b2 reindex --dry-run previews the same decision, writing nothing.

Ground truth: graph.rs · one_note_reindex_equals_full — incremental re-index of one note yields a byte-identical edge set to a full rebuild, and a second reindex is identical again (idempotent). chunks.rs proves replace-not-accumulate; ingest_resolver.rs confirms a link resolves from either authored form; project_embed.rs pins the projection/embedding split (project touches no vectors; embed fills exactly the missing set; project→embed ≡ a fused reindex); dry_run.rs proves the preview writes nothing. ↳ the indexing deep dive covers incremental skip, --force, batching.

The schema — a derived projection

Every table is a projection of (Markdown); nothing here is a source of truth. The schema is derived from the data model — it must satisfy the model, never the reverse.

TableHoldsDerived from
notespath (PK), type, title, created/updated, body_hash — identity is the path; children reference it ON UPDATE CASCADE, so a move is a re-keyMarkdown
chunksper-note structure-aware (qmd) chunks with char offsets, token_count + heading_path, and the text_hash that addresses the chunk's vectorMarkdown
chunks_ftsFTS5 BM25 index (porter unicode61, stemmed — the measured #157 verdict, schema v5), kept in lockstep by triggersderived (FTS5)
embeddingscontent-addressed vectors as plain BLOB rows keyed by the blake3 hash of the chunk text that produced them, created at embed time — not in the base migration; scored in-process (embed::l2_sq)derived (#38, #170)
note_centroidsone normalized centroid per note, maintained by the embed pass — discovery's O(notes) stage-1 shortlistderived (#38)

metaschema_version, embed_model_id, embed_dimbookkeeping

Two schema details do load-bearing work. There is no status column and no lifecycle — an edge exists iff it is written in the Markdown, so origin only records which home it came from (inline body link, or a frontmatter b2_relations: entry). And the vector tables (embeddings + note_centroids) are created outside the base migration, at embed time: their existence is the "this vault has an embedding space" signal the projected-but-unembedded fallbacks key on, and meta.embed_model_id/embed_dim record the space's identity (a device tag folds in — a Metal build is a different space, GH #40). (Removed 2026-07-04: the edge_provenance table, the status column, the origin='suggested' value, and the origin/status CHECK — all gone with the LLM relator.)

The substrate bet. One embedded store answers every query at once — FTS5, vectors, and the typed graph — so b2 similar can join all three in one transaction. No vector extension is involved at all (#38): vectors are plain BLOB tables read with one sequential statement and scored in-process (embed::l2_sq over db::for_each_stored_vector), so the whole thing is one statically-linked binary with stock SQLite. substrate.rs proves a BM25 query and a vector scan run against the same connection.

FLOW ②  Search — hybrid retrieval

crates/b2-core/src/search.rs

BM25 keyword search and brute-force vector KNN run in parallel and fuse with Reciprocal Rank Fusion (Σ 1/(k + rank + 1), k=60). Results resolve up from chunks to notes. On a projected-but-unembedded vault the vector half is skipped and results are BM25-only — degraded honestly, never an error.

# keyword + semantic, fused — one command
$ b2 search "how does forgetting affect recall"
0.0328  spaced-repetition (notes/spaced-repetition.md)
    Spaced repetition exploits the [[concepts/memory|Human memory]] retrieval curve.
0.0161  memory (concepts/memory.md)
    The brain encodes, stores, and retrieves information…

A note's display name is its filename (data-model.md §1) — the fixture's frontmatter title: is inert, read back and preserved, never a second source of truth for the name.

query→ BM25 over chunks_fts⊕ vector scan over embeddings→ RRF (k=60) → top chunks → notes
  • The keyword half sanitizes raw natural language into a safe FTS5 expression — each alphanumeric term double-quoted so nothing is read as an operator, OR-joined for recall. (Punctuation is FTS5 syntax and would otherwise crash the parse — a real bug the eval surfaced.) The index it matches is stemmed (porter unicode61, schema v5) — a measured verdict: the #157 A/B improved 7 BM25-only and 3 hybrid note ranks with every precision probe unmoved (GH #157).
  • A fused-score tie breaks on the dense signal's rank, not on chunk id: RRF over integer ranks lands every score on a discrete lattice, so bit-identical ties are structural — and the secondary key is a policy about which signal to trust in a photo finish, decided by the eval (#156), never left to projection walk order.
  • A graph-filtered variant — "nearest chunks whose note is within k typed hops of note X" — is the embeddings ⨝ chunks ⨝ edges join. It searches within an already-related neighborhood (near ∩ connected). Discovery is its complement (near ∖ connected) — the two are opposites, and confusing them is the trap the engine turns on avoiding.
  • The façade resolves hits to note level: pulls a wide chunk pool, dedups to the best chunk per note, attaches a one-line snippet.
Ground truth: search.rs (8 tests) locks k=60, proves a doc in both lists outranks single-list winners, and pins the join — graph_filtered_search_restricts_to_reachable_notes excludes a text-matching note disconnected from the anchor. Honest scope: under the fake embedder the vector half isn't semantic, so these prove the plumbing, not model quality — that's the out-of-CI eval harness (make eval: hand-labelled retrieval + discovery corpus, BM25/vec-only/hybrid columns, suppression gates; docs/evals/README.md is the overview, the git history and the issue that drove each change are the decision log).

FLOW ③  Similar — surface the connections you haven't made

crates/b2-core/src/discover.rs

b2 similar <note> surfaces the notes most semantically similar to an anchor that you haven't linked yet — instantly, locally, free: a two-stage scan over the vectors already in the index (note_centroids shortlist, then exact chunk-pair max-sim), with no model call and no network. The machine finds the candidates; you supply the judgment and the type (Flow ③ cont.). This is the reason B2 exists — and after the 2026-07-04 pivot it costs nothing per run.

The one idea — a candidate is near ∖ connected

A candidate is a note semantically near the anchor but not already connected — the complement of the graph, not the intersection. Mechanism, per anchor, in discover::candidates:

anchor's stored chunk vectors→ centroid shortlist — O(notes)− reachable_within(anchor, 1)→ exact max-sim per shortlisted note→ rank → cap(limit) — the ranked list, always
  • No re-embedding, no model call. Each anchor chunk's already-stored vector is the KNN query — discovery is passage↔passage, so the anchor is its indexed vectors, never an embed_query whose asymmetric prefix is the wrong side. The run reads only the vectors reindex already wrote.
  • Max-sim to the note. Every other note scores by its single best chunk-pair similarity, carrying the winning chunk as the evidence passage B2 shows you.
  • Subtract the graph — the only graph read. reachable_within(anchor, 1) (anchor + direct neighbors) is removed. Distance is exclusion-only: a 2-hop note (triadic closure — "you linked A–B and B–E but never A–E") survives, ranked purely by semantic score.
  • The ranked list is always served — limit is a cap, not a promise (invariants.md D1, GH #196/#197/#200). Discovery answers a relative question, so no statistic gates the list: the per-anchor z existence gate that used to empty it was measured reading a coherent single-domain vault — everything related, so nothing "stands out" — as "nothing relates", darkening 16 of 17 panes, and was retired rather than retuned. The z survives ungated as the strength band's input, and an empty result means only that nothing unlinked has stored vectors to compare. The disclosure question was reopened once and closed again: a mutual-nearest-neighbour fold lost its bake-off outright (GH #200 — every depth that stops hiding a labelled relative is past the depth that still empties a loner's view, and the safe depths are the same fraction of two different pools rather than one constant), so the served list is still undivided.

In our fixture the two notes are directly linked, so each is excluded as the other's candidate — a correctly empty result, which is exactly the assertion discover.rs pins.

what b2 similar shows you per candidate
  • path + title — the note to consider connecting to.
  • similarity score — best chunk-pair max-sim (negated L2 distance; higher is nearer) — plus the candidate's z, what the desktop's strength band derives from.
  • evidence passage — the candidate's chunk that achieved the score, so you can judge the link at a glance.

You are the precision gate. There is no LLM adjudicating pairs and nothing is proposed on your behalf — B2 ranks, you decide, and you commit the ones worth a real connection with b2 link (or a body link of your own).

Ground truth: discover.rs pins the complement — direct neighbor excluded, disconnected near note kept, 2-hop note survives, deterministic ranking (ties broken by path), and an empty result when the anchor has no vector space yet; discover_surfacing.rs pins always-serve with a purpose-built geometric embedder — the ranked list served with its z on every row, a diffuse anchor's pane served rather than darkened, tiny pools band-less but complete, fake spaces statistic-less, and banding the only thing that changes at the statistics threshold. (Removed 2026-07-04: the Relator seam, the ClaudeRelator, the generate/suggest pipeline, and their tests — the per-pair LLM cost didn't scale to a 1000+ note vault. Candidate generation is all that remains, and it was always the free, deterministic stage.) ↳ the discovery run deep dive walks a full b2 similar.

FLOW ③ cont.  Link — commit a chosen connection

crates/b2-core/src/note.rs (add_relation) · re-projected via ingest.rs

You saw a candidate worth connecting; now you commit it. There are exactly two ways a connection becomes real, both authored in Markdown — B2 never proposes an edge on its own, and there is no inert queue to accept from.

a candidate from b2 similar→ your judgment → b2 link (frontmatter) or a [[link]] you write in the body → reindex → active edge
  • b2 link <src> <dst> [--type <verb>] [--explanation …]. B2 resolves both refs (each a path, with or without the .md), builds the typed-link string against the target's current path — a bare [[path]], no alias, since a note's title is its filename — and appends it to the source note's frontmatter b2_relations: (Markdown-first — never the body). --type defaults to references; the palette is the closed three-verb core, and a non-core verb is refused here (a hand-written one is still tolerated).
  • Then it re-projects the note (Flow ①), so the edge materializes as origin=frontmatter straight from the line just written. Committing is a projection of an authored line, not a bespoke index write — which is what keeps every edge traceable to a real line in the Markdown.
  • Or write a body link yourself — a bare [[path]] or [[path|title]], anywhere in prose. That edge is always untyped (references): the body has no B2 syntax, so no verb and no "why" is ever parsed out of it — typing is frontmatter's job alone. B2 reads the body link on the next reindex; it never writes the body. No status, no tombstone, no provenance — an edge exists iff it is written in the Markdown.
what b2 link writes into the source note
---
type: concept
title: "Spaced repetition"
b2_relations:
  - "supports [[concepts/memory.md]]"  # ← appended
---

Frontmatter only. The body is byte-unchanged. On the next reindex this line re-derives as an active origin=frontmatter edge — no separate record anywhere.

Ground truth: the write path is note.rs · add_relation — one YAML-quoted typed-link appended to b2_relations:, the body byte-unchanged (frontmatter.rs, roundtrip.rs). The committed edge then re-derives as origin=frontmatter on reindex, identical to a hand-authored b2_relations: line (graph.rs).

The write discipline — losslessness & surgical edits

crates/b2-core/src/note.rs · add.rs · mv.rs

The vault stays the human's. A parsed note keeps its raw text verbatim and records only the byte spans of the frontmatter block; serialization returns those raw bytes. So parse → serialize → parse is byte-identical — unknown keys, comments, odd whitespace, a missing final newline all survive. Against that backdrop, every byte B2 writes is the mechanics of a command you invoked — B2 makes no unbidden writes at all (GH #170 removed the last one, the b2id stamp):

Frontmatter, surgical
  • add_relation — one YAML-quoted typed-link appended to b2_relations: (the b2 link path).
  • write_frontmatter — a splice of the human's own frontmatter bytes from the desktop drawer; the body is untouched.
Whole-file ops (CRUD)
  • b2 add — create a note (minimal frontmatter; nothing is added on first sight).
  • b2 mv — move/rename + rewrite inbound [[oldpath]] link text.
  • write — the editor's body splice, guarded by a content-hash revision. Never authored by B2.
b2 mv never breaks the graph. A note's identity is its path, so a move is a re-key, not a rebuild: children reference notes(path) ON UPDATE CASCADE, and the same statement that renames the row carries chunks, vectors and edges across with it — neighbors/backlinks show the same set before and after, and not one chunk is re-embedded. The human convenience-copy [[oldpath|alias]] text is repaired too, and only in the exact inbound files the materialized graph names (db::inbound_edge_targets — bounded, never an O(vault) scan). A byte-preserving rewrite swaps only the target token; a prefix-sharing [[foo-bar]] is never touched when moving foo. Move a note outside B2 and the bargain is the honest one: the links dangle, visibly, until you repair them.
Ground truth: roundtrip.rs pins losslessness; frontmatter.rs pins the surgical frontmatter writes; mv.rs pins graph-unchanged, byte-exact inbound diffs, prefix-safety, clean errors on clobber/invalid dest, that a move reuses every vector, and that an out-of-band move dangles its backlinks while re-embedding nothing; add.rs pins create-and-project and clobber refusal.

The AI seams — a fake for CI, a real model for users

Every AI part sits behind a swappable trait defined in b2-core. The engine is built and tested against a deterministic fake; a real model drops in through the identical seam with no schema or flow change. This is the "build for tomorrow's model" tenet made mechanical — and it is why the whole suite runs with no live model, no wall clock, and no random ids. There are two, and only the first is wired up to a front end today.

Embedder — embed::Embedder

Fake: FakeEmbedder blake3-hashes text into a vector — identical text → identical vector, deterministically. KNN is reproducible; not semantic. Real: b2-embed::LocalEmbedder, candle BERT, CLS-pool + L2-normalize (so the in-process L2 ranks by cosine), asymmetric query prefix, dim read from the model's own config.json.

The swap is safe by construction. meta records (embed_model_id, embed_dim); on a model/dim change the vector tables (embeddings + note_centroids) are dropped + recreated empty so a full re-embed follows. Opening a vault never mutates the vector space; a stale search fails fast with ModelMismatch rather than returning silently-wrong results.

LlmProvider — llm::LlmProvider · engine-only so far

The chat seam behind flow ④, Vault::ask (chat.rs): condense a follow-up into a standalone query → retrieve passages → assemble the grounded prompt → stream tokens up through the caller's callback → resolve [n] citation markers back to (path, excerpt). Fake: FakeLlm echoes citation markers for its passages, so the whole flow is testable with no model. Sync, no tokio; the callback's return value is cooperative cancellation at token granularity, in the trait from day one because that is the kind of contract that calcifies.

The contrast with the embedder is the point. Chat carries no index identity: nothing it produces is stored — no meta row, no response cache, session-only history — so swapping chat models never touches the index and is a config change, not a reindex. It is a pure reader, and its output is untrusted content, sanitized at the render surface like any other Markdown. Neither adapter exposes it yet — there is no b2 ask and no chat pane; the seam and the flow are built and tested, the front ends are not.

The relator seam was cut 2026-07-04. B2 briefly had a second seam — a Relator (real: a Claude-backed ClaudeRelator in b2-relate) that typed and explained every candidate pair. On a real 1000+ note vault the per-pair latency and dollar cost didn't scale, and a per-pair LLM adjudicator is exactly the "model-compensating machinery" the Bitter-Lesson tenet says to defer. So the seam, the crate, and the suggestion queue are gone; the human is the precision gate. The seam that did land next is the chat seam above — a reader that stores nothing, not an adjudicator in the discovery loop. If another lands it's a reranker (post-fusion, changes ordering not the store) — not a return of the relator.
the relation vocabulary — closed core + tolerated tail · relation.rs
  • references → referenced-by  (neutral)
  • supports → supported-by  (for)
  • contradicts ↔ (symmetric)  (against)

A closed three-verb stance core is your typing palette on b2 link --type (which refuses anything else) and what all queries rely on; each ships a display-only inverse label and a symmetry flag (inbound neighbors render the inverse; only one directed row is ever stored). Three, not thirty, because stance is the one thing embedding similarity cannot infer — "these two notes are about the same thing" is what the vectors already tell you; whether one backs or fights the other is what only a human knows. A tail verb a human writes by hand (e.g. inspired-by) is kept verbatim, never dropped, treated as opaque and directed. Expressiveness lives in the tail; reliability lives in the core — and the core is a relaxable policy, not a structural assumption: adding a verb is one entry in relation::CORE.

The command surface — a dumb adapter over one typed façade

crates/b2-core/src/vault.rs · crates/b2-cli/src/main.rs

Every engine module is called directly only by the integration tests. The Vault façade is the single typed entry point whose only clients are the two adapters — the CLI and the Tauri desktop host — it owns the connection and the injected embedder, and returns display-ready view structs (NeighborView, SearchResult, ExplainView, the discovery candidate view, …). The b2 binary parses args, picks the embedder, calls the façade, and prints — human, or --json for agents; each desktop #[tauri::command] is deserialize → one façade call → serialize, reusing the same view types as its IPC contract.

The invariants that hold it together

Almost every choice above serves one of these. Each is pinned by the suite.

Grounded in the tests

Nothing here is aspirational: the suite is the executable specification, integration-first, and every property above is asserted in it. Most tests share the golden vault, copied into a temp dir before every run, at two fixed paths — concepts/memory.md and notes/spaced-repetition.md — which are the notes' identities, so every assertion names them directly. Determinism is a hard requirement of the core — no wall clock, no randomness; timestamps are passed in.

Not yet built

An honest architecture names its boundaries. Connection discovery is built — it is now b2 similar (surface) + b2 link (commit), local and free; the LLM relator was cut, not deferred. What remains is tuning, scale, and packaging — tracked in GitHub Issues, not gaps that slipped through.

  • Semantic quality in CI. The engine suite runs on the deterministic fake embedder, so it proves plumbing, not ranking quality. The real model is measured by the out-of-CI eval harness (make eval): a hand-labelled retrieval + discovery corpus scoring BM25 / vector-only / hybrid note ranks, passage ranks, and per-mate discovery ranks (with a zero-empty-panes assertion on a second, deliberately single-domain fixture, enforced in the exit code) — plus a model-free rank-stability probe (make stability) for what a small corpus is structurally blind to, and a real-vault calibration command (make calibrate) for what no synthetic corpus can claim alone. Every shipped verdict — porter stemming (#157), the chunker config (#44), the discovery floor in (#150) and back out (#196/#197) — traces to a recorded run on the issue that drove it and the commit that shipped it; docs/evals/README.md is the overview. Model quality never flakes CI.
  • Cold-index scale, CLI side. Incremental reindex is done, projection and embedding are decoupled (keyword-first: a cold vault is searchable before it's embedded), the desktop runs the embed pass as a cancellable background task, and the CLI's cross-process story is complete — b2 reindex & backgrounds through the shell, b2 status names the running pid, and b2 reindex --cancel signals it onto the same cooperative-cancel path as Ctrl-C. Still open: a smaller/quantized embedder — it composes behind the existing seam.
  • Deferred, behind clean seams. A cross-encoder reranker (the likely next seam — changes ordering, not the store), query expansion, and the actual packaging/distribution build. (The qmd chunker, once on this list, shipped — the eval-validated #44 verdict; see the indexing deep dive.)
